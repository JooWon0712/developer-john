# 서비스 도메인 관리 정책

정리일: 2026-11-02.

`developer-john.com`은 개인 소개와 작업을 보여주는 홈페이지이자 전체 서비스의 진입점으로 운영한다. 각 서비스는 기존 사이트의 경로에서 제공하거나, 이용 대상과 운영 방식에 따라 서브도메인으로 분리한다. 서비스가 늘어나도 메인 사이트의 `/services`에서 찾아갈 수 있게 한다.

이 문서는 앞으로 주소를 정하고 변경할 때 적용할 운영 기준이다. 아래의 후보 주소는 실제 등록·배포된 주소와 구분하며, 이번 정리로 기존 공개 URL이나 DNS·NAS 설정을 변경하지 않는다.

## 메인 사이트와 서비스의 역할

| 구분 | 주소 | 역할 |
| --- | --- | --- |
| 개인 홈페이지 | `https://developer-john.com/` | 홈, 소개, 개인 작업과 관심사를 보여준다. |
| 전체 서비스 목록 | `https://developer-john.com/services` | 공개 중인 서비스를 소개하고 실제 이용 주소로 연결한다. |
| 메인의 별칭 | `www.developer-john.com` | 별도 사이트로 키우지 않는다. 대표 주소는 www가 없는 주소로 통일한다. |
| 독립 서비스 또는 서비스군 | `<이름>.developer-john.com` | 해당 서비스의 화면과 기능을 제공한다. 서비스 안에서 메인 홈페이지로 돌아갈 수 있게 한다. |

메인 사이트의 메뉴는 개인 홈페이지의 탐색을 담당한다. 각 서비스의 게임·이벤트·테스트 메뉴는 해당 서비스 안에서 구성한다. 공개 준비가 끝난 서비스만 전체 서비스 목록에 추가한다.

## 서브도메인을 나누는 기준

자체 이름, 별도 이용 대상과 화면, 독립적인 기능·업데이트 주기가 필요한 서비스는 서브도메인으로 분리하는 것을 기본 방향으로 한다. 기존 서비스와 화면·기능을 공유하는 작은 도구는 내부 경로에 추가한다.

- 게임 정보처럼 여러 콘텐츠를 같은 기능으로 제공하면 서비스군 하나로 묶는다. 새 게임이나 이벤트는 그 안의 경로로 추가한다.
- 그림 성향 탐색처럼 부모·아이에게 맞는 별도 참여 흐름이 필요하면 독립 서비스로 검토한다. 테스트가 늘어도 테스트마다 서브도메인을 만들지는 않는다.
- 독립된 브랜드로 운영할 필요가 생기면 별도 도메인을 검토한다. 첫 버전부터 도메인을 추가 구매하는 것을 기본으로 삼지는 않는다.

| 대상 | 주소 후보 | 구분 |
| --- | --- | --- |
| 게임 정보 서비스군 | `games.developer-john.com` | 향후 개편 후보. 이름과 이전 시점은 미정이다. |
| 부모와 아이의 그림 성향 탐색 | `kids.developer-john.com`, `play.developer-john.com`, `mind.developer-john.com` 또는 서비스 이름 | 대상과 공개 이름을 정한 뒤 하나를 선택한다. |

후보 이름을 문서에 적었다는 이유로 DNS, 공개 메뉴, 광고·분석 설정을 미리 추가하지 않는다.

## 이름과 경로 규칙

서브도메인 이름은 소문자 영문·숫자·하이픈으로 정하고, 서비스의 의미가 오래 유지되는 짧은 이름을 사용한다. 호스트 이름에는 이벤트 연도나 출시 순번을 넣지 않고 콘텐츠 경로에서 구분한다.

게임 서비스라면 `games.developer-john.com/the-division-2/<event-slug>`, 테스트 서비스라면 `<서비스>.developer-john.com/tests/<test-slug>`처럼 구성할 수 있다. 이는 새 서비스의 경로 예시이며 현재 디비전2 URL의 변경안은 아니다.

한국어는 각 사이트의 기본 경로를 사용하고, 영어를 제공하면 같은 호스트의 `/en/...` 경로로 대응시킨다. 언어별 서브도메인은 추가하지 않는다. 메뉴·터미널 제목에 경로를 표시할 때도 실제 경로를 기준으로 하고 `/home/john` 같은 가상 접두사는 붙이지 않는다.

## 코드와 배포 관리

메인과 서비스 코드는 현재 `developer-john` 저장소에서 함께 관리하는 것을 기본으로 한다. 서브도메인이 생겨도 Git 저장소를 새로 만들어야 하는 것은 아니다. 함께 사용하는 언어·메타데이터·UI 기능은 공통으로 두고, 서비스의 문항·채점·게임 보상 데이터 같은 고유 기능은 서비스별로 관리한다.

도메인 분리와 실행 앱 분리는 따로 판단한다. 같은 앱에서 여러 호스트를 처리할 수도 있으며, 독립적인 배포나 설정이 필요하면 같은 저장소 안에서 앱·빌드·컨테이너를 나눈다. 실제로 두 번째 앱을 만들 때 필요한 구조로 확장하고, 현재 단계에서 폴더나 빌드 체계를 일괄 개편하지 않는다.

현재 `NEXT_PUBLIC_SITE_URL`은 빌드당 하나의 기준 주소를 만들고, NAS 배포 스크립트도 본 도메인을 빌드 인자로 사용한다. 새 호스트를 같은 앱으로 받을 때는 호스트별 링크·메타데이터·리디렉션을 처리해야 하며, 별도 앱으로 배포할 때는 해당 앱의 기준 주소와 배포 대상을 분리한다. DNS만 연결하면 앱 설정까지 완성되는 것으로 보지 않는다.

## 주소 운영 대장

주소를 추가하거나 바꿀 때 이 표를 갱신한다. 상태는 `기획`, `개발`, `운영`, `종료`로 구분한다. 후보 주소는 확정된 대표 URL과 구분해 기록한다.

| 대상 | 대표 URL 또는 후보 | 상태 | 다음 주소 작업 | 최근 정리 |
| --- | --- | --- | --- | --- |
| 개인 홈페이지 | `https://developer-john.com` | 운영 | 현재 대표 주소 유지 | 2026-11-02 |
| 디비전2 | `https://developer-john.com/services/game/the-division-2` | 운영 | 이벤트 종료 후 공개 범위와 개편 시점 정리 | 2026-11-02 |
| NAS Desktop 소개 | `https://developer-john.com/services/tools/nas-desktop-app` | 개발 | 로컬 소개 페이지 완료, 홈페이지 배포 대기 | 2026-11-02 |
| PC 인터넷 모니터 소개 | `https://developer-john.com/services/tools/pc-internet-monitor` | 개발 | 로컬 소개 페이지 완료, 홈페이지 배포 대기 | 2026-11-02 |
| 게임 서비스군 개편 | `games.developer-john.com` 후보 | 기획 | 서비스 범위·이름 확정 후 연결 준비 | 2026-11-02 |
| 그림 성향 탐색 | 대표 URL 미정 | 기획 | 공개 이름과 서브도메인 선택 | 2026-11-02 |

공개할 때는 서비스별로 실행 앱·배포 대상, DNS·인증서·프록시 연결, GA 적용 여부와 측정 ID, 광고 적용 여부도 기록한다. 배포 절차는 [NAS 배포 안내](deploy-synology.md)에 관리하고, 접속 정보·개인키·비밀번호는 이 문서나 Git에 저장하지 않는다.

Windows 앱의 소개 페이지는 메인의 `/services/tools/...`에서 제공한다. 실행 파일·버전은 각 프로그램의 GitHub Releases에서 관리하므로 소개만을 위한 서브도메인은 추가하지 않는다. 두 프로그램의 기존 소스 저장소도 각각 유지한다.

## 새 주소 공개 절차

1. 서비스 범위, 대표 호스트, 내부 경로와 제공 언어를 정한다.
2. DNS와 해당 호스트를 포함하는 HTTPS 인증서, NAS 역방향 프록시를 연결한다. 다른 서비스의 배포 대상과 충돌하지 않게 한다.
3. 앱의 기준 주소, 내부 링크, canonical·언어별 대응 주소·공유 이미지 URL을 해당 호스트에 맞춘다. HTTP는 해당 서비스의 대표 HTTPS 주소로 이동시킨다. 별칭이 있으면 대표 주소로 모으고 경로·쿼리를 유지한다.
4. 루트·상세 주소 직접 접속, 새로고침, 언어 전환, 공유 미리보기와 주소 이동을 확인한다. 변경된 기능에 맞는 빌드·검사와 운영 설정을 확인한다.
5. 검증한 주소를 운영 대장과 메인 서비스 목록에 반영한다.

개발·시안은 로컬에서 확인한다. 공개 미리보기 주소가 필요할 때만 별도로 만들고 검색 노출과 운영 통계 수집을 구분한다. 모든 새 주소를 받는 와일드카드 라우팅·GA 허용은 기본 설정으로 두지 않는다.

## 기존 공개 주소의 이전

공개된 주소는 새 서비스가 준비됐다는 이유만으로 바꾸지 않는다. 같은 콘텐츠를 새 주소로 옮길 때 기존 URL과 새 URL의 대응표를 만들고 영구 리디렉션을 적용한다. 한국어·영어, 상세 경로, 쿼리와 보상 위치 해시가 유지되는지 확인한다. 내부 링크와 canonical·공유 주소도 새 주소로 맞추며 리디렉션의 유지 기간을 기록한다. [Google 사이트 이전 안내](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)

보상 기록 등 `localStorage` 데이터는 출처별로 저장된다. 본 도메인에서 서브도메인으로 이동하면 기존 기록을 자동으로 읽을 수 없으므로, 이전 전에 기록을 계속 사용할 필요와 전달 방법을 정한다. 리디렉션만으로 기록이 이전된다고 안내하지 않는다. [MDN localStorage 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

## 이벤트와 서비스의 종료

이벤트 종료와 서비스 전체 종료는 구분한다. 이벤트가 끝나면 진행 중 목록에서 제외하고, 기존 공유 주소에는 종료 안내를 남기는 방식을 기본으로 한다. 원문까지 계속 제공할지, 종료 안내만 제공할지는 콘텐츠 정리 때 결정한다. 완전 삭제를 선택하면 해당 페이지의 제거와 검색 노출도 함께 정리한다.

동일한 콘텐츠의 새 주소가 있을 때만 이전 주소를 연결한다. 종료된 이벤트 주소를 관련 없는 새 서비스나 메인 홈으로 일괄 이동시키지 않는다. 소스·이미지·디자인 시안·프리뷰 HTML은 보관한다.

레드 문 가이드는 사용자가 설명한 11월 3일 종료 이후 공개 범위를 정리하는 대상으로 둔다. 실제 종료를 확인한 뒤 적용하며, 이 정책만으로 자동 삭제나 예약 종료를 실행하지 않는다. 다음 게임 서비스 개편과 기존 가이드의 종료 처리는 별도 작업으로 진행한다.

## 방문 통계와 광고

GA는 서브도메인마다 새 계정을 만들지 않고 기존 계정 아래서 관리한다. 메인과 같은 목적으로 통합 분석할 서비스는 같은 속성을 사용할 수 있고, 이용 대상·측정 목적이 달라 별도 통계가 필요한 서비스는 속성을 분리한다. 적용 여부와 측정 ID는 서비스별로 정하며, 이벤트·테스트 하나마다 속성을 새로 만들지는 않는다.

현재 코드의 GA 허용 주소는 본 도메인과 www의 HTTPS 주소 두 개다. 새 서브도메인을 만들면 측정 허용 주소를 명시적으로 추가하거나 별도 앱의 측정 설정을 마련해야 한다. 통합 측정을 선택하면 태그·쿠키 도메인·자기 사이트 유입 처리도 함께 확인한다. [Google 도메인 간 측정 안내](https://support.google.com/analytics/answer/10071811?hl=ko)

애드센스는 본 도메인이 승인된 뒤 같은 게시자 계정을 일반 서브도메인에도 사용하는 방향으로 관리한다. Google은 기존 사이트의 일반 하위 도메인을 사이트 목록에 별도로 추가·관리하지 않도록 안내한다. 광고 적용 여부와 배치는 각 서비스에서 결정하며, 승인을 받았다고 광고 코드가 자동 적용되는 것은 아니다. [Google 하위 도메인 관리 안내](https://support.google.com/adsense/answer/12170421?hl=ko)

같은 판매자·게시자 구성이면 본 도메인의 ads.txt를 기준으로 관리한다. 구성이 다른 서브도메인은 별도 선언 필요성을 확인한다. 부모·아이용 서비스는 이용 대상에 맞는 광고 설정을 정한 뒤 도입한다. [Google ads.txt FAQ](https://support.google.com/adsense/answer/9785052?hl=ko), [연령 제한 콘텐츠 처리 안내](https://support.google.com/adsense/answer/3248194?hl=ko)

## 지금 유지할 상태와 다음 결정

현재 메인과 디비전2 주소는 유지한다. 새 서비스의 실제 공개 전에는 도메인 이름과 실행 앱·배포 방식을 정하고 이 정책에 따라 연결한다. 게임·그림 성향 탐색의 구체적인 서브도메인 이름은 미정이다.

기능 기획과 문항은 [서비스 계획](service-plan.md), [그림 성향 탐색 기획](illustrated-personality-test-plan.md), [첫 제작안](illustrated-child-test-mvp.md)에서 이어간다. 도메인 운영 기준은 이 문서를 기준으로 관리해 같은 정책을 여러 문서에 중복 작성하지 않는다.
